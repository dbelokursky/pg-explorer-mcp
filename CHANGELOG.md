# Изменения

## Не выпущено

- Вызов на несколько стендов начинает следующий стенд, только если до 25 секунд хватит и на подключение,
  и на запрос до его таймаута; раньше в запас входило только подключение, и последний стенд мог вывести
  вызов за 30 секунд, которые ждёт клиент.
- Описания инструментов короче: в режиме стендов `tools/list` ужался с 9,5 до 7 тысяч символов, для одной базы —
  с 5 до 4,3 тысячи. Правила про `stand`, `schema` и `database` сказаны один раз в инструкциях сервера, а не в
  каждом инструменте; тест не даёт объёму расти обратно.
- CI на PR стал вдвое дешевле: без macOS и с PostgreSQL 13, 16 и 18 вместо шести версий; полный набор
  идёт на push в `develop` и `main`. Сборка архива релиза на PR — только когда менялись её исходники.
- Инструмент `compare_schema` в режиме стендов, во всех профилях: сравнивает структуру одной схемы на двух
  стендах — таблицы и представления, колонки (тип, `NOT NULL`, значение по умолчанию), ограничения и
  индексы — и показывает, что есть только на одном стенде и что отличается; данные не читаются. Структура
  берётся из каталога под учёткой схемы на каждом стенде, три запроса на стенд. Схема, которой нет в базе
  одного из стендов, — отдельная ошибка, а не «только на A: всё».
- Один запрос на нескольких стендах за один вызов: в режиме стендов `run_select` и `search_schema` принимают
  вместо `stand` аргумент `stands` — имена через запятую или шаблон (`dev1,dev2`, `dev*`), не больше 10
  стендов. Стенды опрашиваются по очереди, в ответе на каждый своя секция под строкой `стенд / база / схема`;
  недоступный стенд, стенд без учётки схемы или ошибка запроса — одна строка под его заголовком, остальные
  стенды отвечают. Строки `run_select` и совпадения `search_schema` делятся между стендами, не меньше 10 на
  стенд; вызов укладывается в 25 секунд, остальные стенды перечисляются как не проверенные. Журнал запросов
  пишет на такой вызов одну запись с итогом по каждому стенду (`stands`).
- Тесты на то, что раньше проверялось только без базы: TLS во всех режимах `PGSSLMODE` через
  TLS-прослойку перед настоящим PostgreSQL (сертификат делает `openssl`), включая отказ от чужого
  сертификата и несовпадение имени хоста; срабатывание `statement_timeout` на долгом запросе и то, что
  сокет его дожидается; подключение через Unix-сокет.
- Сервер, который принял подключение и закрыл его при входе без сообщения, объясняется отдельно:
  обычно это пароль или `pg_hba.conf`. Так на Windows выглядит отвергнутый пароль, когда сброс
  соединения стирает сообщение сервера; раньше это была безликая «network error».
- Много стендов в одной записи (ADR 0006). С `PG_MCP_STANDS` сервер читает реестр в формате
  `pg_service.conf` (`~/.pg-mcp/stands.conf` и `~/.pg_service.conf`, секции `стенд.база.схема`), и каждый
  инструмент принимает `stand`, а для чтения данных — `schema`: сервер подключается под учёткой этой схемы.
  Новый инструмент `list_schemas`; структура по всему стенду берётся из каталога, только по схемам реестра;
  каждый ответ начинается со строки `стенд / база / схема`, журнал запросов пишет стенд и схему.
  Подключения открываются по требованию, открытыми держится не больше 8 (`PG_MCP_MAX_CONNECTIONS`).
  Без `PG_MCP_STANDS` или без стендов в реестре всё работает как раньше. Запись регистрирует
  `PG_MCP_STANDS='*' install.py --name stands`; проверке установки достаточно найденных стендов.
- Быстрый отказ недоступного стенда. Хост, который не ответил (нет маршрута, таймаут, отказ порта), в
  пределах вызова больше не пробуется ни под одной учёткой, а вторая учётка базы пробуется, только когда
  сервер ответил и отверг первую: стенд за упавшим VPN стоит один таймаут, а не один на каждую учётку
  и базу, и вызов укладывается в 30 секунд ожидания клиента. «Нет маршрута до хоста» объясняется
  отдельно — подключите VPN. Хост, который принимает соединение и молчит, раньше ронял вызов ошибкой
  сервера, теперь даёт ту же подсказку про таймаут.
- Таймаут сети разделён: подключение ждёт `PG_MCP_SOCKET_TIMEOUT_S` (30 секунд, для стендов 10), а
  открытый сокет — не меньше таймаута запроса плюс 5 секунд: долгий запрос кончается ошибкой PostgreSQL,
  а не обрывом соединения и повторным запуском.
- Сервер, который принял подключение и закрыл его при входе без сообщения, объясняется отдельно:
  обычно это пароль или `pg_hba.conf`. Так на Windows выглядит отвергнутый пароль, когда сброс
  соединения стирает сообщение сервера; раньше это была безликая «network error».

  недоступный стенд, стенд без учётки схемы или ошибка запроса — одна строка под его заголовком, остальные

- Инструмент `compare_schema` в режиме стендов, во всех профилях: сравнивает структуру одной схемы на двух
  стендах — таблицы и представления, колонки (тип, `NOT NULL`, значение по умолчанию), ограничения и

- Архив для тех, у кого нет git: пуш тега `vX.Y.Z` собирает `pg-mcp-X.Y.Z.zip` из дерева тега без
  `.github`, проверяет, что сервер запускается из распакованного архива (`install.py --check`), и
  публикует GitHub Release с `SHA256SUMS` и заметками из раздела этой версии здесь; версия тега сверяется
  с версией в файлах. README: установка и обновление из архива.
- Несколько баз из одного клона: `install.py --name sales` регистрирует сервер `pg-sales` рядом с `pg`, со

## 0.3.0 — 2026-10-22

- Английский и русский (ADR 0004): описания инструментов, ответы, подсказки и вывод `install.py`.
  Язык задаёт `PG_MCP_LANG` или `install.py --lang`, иначе локаль системы; `status` показывает его.
  Модель просят отвечать пользователю на его языке.
- Инструмент `search_schema` во всех профилях: ищет таблицы, представления и колонки по фрагменту имени
  или комментария во всех доступных роли схемах, не больше 100 совпадений. Для больших баз, где
  `list_tables` упирается в 200 записей.
- Журнал запросов агента (ADR 0005): с `PG_MCP_QUERY_LOG` каждый вызов инструмента пишется строкой JSON —
  кто, что, чем кончилось и сколько строк вернул запрос, без самих данных. Файл с правами 600, ссылка
  на его месте отвергается, сбой записи не мешает работе и виден в `status`.
- Подробный README на английском (`README.md`) и русском (`README.ru.md`): установка по шагам для macOS,
  Linux и Windows, примеры ответов, профили, язык, настройки, роль для DBA и разбор частых сбоев.
- Интеграционные тесты в CI на PostgreSQL с 13-й по 18-ю. До 14-й версии таблица без статистики
  неотличима от пустой, и `list_tables` пишет «пусто или статистику ещё не собирали», а не «~0 строк».
- Раскладка по рекомендациям PyPA: пакет в `src/pg_mcp/`, сторонние пакеты в `src/pg_mcp/_vendor/`,
  запуск из клона — `python -I run.py`, после установки — `pg-mcp` или `python -m pg_mcp`.
- `pyproject.toml` с метаданными и настройками инструментов, окружение разработки на uv с `uv.lock`.
- ruff вместо flake8, mypy в режиме strict, тесты на pytest с покрытием по веткам (порог 95%), pre-commit.
- CI на uv: Linux, Windows и macOS под Python 3.9 и 3.14; dependabot для Actions и инструментов.

## 0.2.0 — 2026-10-22

- Инструменты `describe_table`, `sample_rows`, `explain_query` и `run_select`.
- Профили групп `schema`, `explore` (по умолчанию) и `analyst`: `install.py --profile` или `PG_MCP_PROFILE`.
- Политика SQL только на чтение (ADR 0002): проверка текста запроса, транзакция `READ ONLY` с обязательным
  откатом на каждый запрос агента, скрипт роли для DBA `docs/role.sql`.
- Бюджет ответа: каждый ответ укладывается в `PG_MCP_MAX_RESPONSE_CHARS` символов (по умолчанию 8000).
- Ревизия MCP 2026-07-28 без рукопожатия: `server/discover`, версия протокола в `_meta` каждого запроса.
  Клиенты ревизий 2024-11-05 — 2025-11-25 работают, как раньше.
- Подсказки при неверном пароле, несуществующей базе и отказе от TLS.
- Проверка целостности `server/vendor` и flake8 в CI.
