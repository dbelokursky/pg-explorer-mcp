# Разработка pg-mcp

## Окружение

Нужен [uv](https://docs.astral.sh/uv/). Он сам поставит Python 3.9 (версия закреплена в
`.python-version`) и инструменты разработки ровно тех версий, что записаны в `uv.lock`:

```bash
uv sync
```

Сам сервер по-прежнему работает без зависимостей. Всё, что ставит `uv sync`, нужно только
для разработки и проверок.

Один раз включите хуки, чтобы проверки шли перед каждым коммитом:

```bash
uvx pre-commit install
```

## Проверки

| Команда | Что делает |
|---|---|
| `uv run pytest` | тесты; интеграционные без базы пропускаются |
| `uv run pytest --cov` | тесты с покрытием по веткам; порог 95% задан в `pyproject.toml` |
| `uv run ruff check --fix` | линтер с автоисправлениями |
| `uv run ruff format` | форматирование |
| `uv run mypy` | проверка типов в режиме strict |
| `uv run python scripts/check_vendor.py` | целостность `src/pg_mcp/_vendor` |
| `python3 scripts/client_smoke.py --qwen "$(command -v qwen)"` | проверка в настоящем клиенте, Qwen Code (`npm install -g @qwen-code/qwen-code`), по переменным `PG*`; модель не нужна |
| `python3 scripts/querylog_report.py <журнал> [--since ДАТА] [--until ДАТА] [--by user\|tool\|stand\|day] [--format text\|json\|csv]` | сводка по журналу запросов (`PG_MCP_QUERY_LOG`) для администратора группы: вызовы по инструментам, пользователям и стендам, медиана и 95-й процентиль, самые долгие и отклонённые проверкой SQL запросы; база не нужна |
| `python3 scripts/agent_eval.py` | прогон типовых вопросов через настоящую модель на демо-базе: какие инструменты она вызвала и что ответила; нужны Ollama с моделью и Qwen Code, см. ниже |

Интеграционные тесты ходят в настоящий PostgreSQL. Они создают и удаляют схемы `mcp_it`,
`mcp_it_archive`, `mcp_it_role` и роли `mcp_it_agent`, `mcp_it_login`, а тесты стендов — схемы
`mcp_it_billing`, `mcp_it_orders`, одноимённые роли и вторую базу `mcp_it_stand` (для неё нужен
суперпользователь), а тест демо-базы — базу `pg_mcp_demo_it` и роль `mcp_demo_it_agent`; тестам роли нужен `psql`, тестам TLS — `openssl` (они ставят перед сервером
TLS-прослойку со своим сертификатом, самому серверу TLS не нужен):

```bash
PG_MCP_IT=1 PGHOST=localhost PGDATABASE=pg_mcp_test uv run pytest --cov
```

CI гоняет то же самое, но на PR — сокращённый набор, а на push в `develop` и `main` и ночью на
`develop` — полный. На PR: линтеры и типы, тесты на Linux и Windows под Python 3.9 и 3.14,
интеграционные тесты на PostgreSQL 13, 16 (покрытие) и 18, интеграционные тесты на Windows с
PostgreSQL 17, проверка в Qwen Code и загрузка выгрузки для pgAdmin в настоящий pgAdmin (Docker-образ
`dpage/pgadmin4`); сборка архива из `release.yml` — только если менялось то, из чего он собирается. В
полном наборе к этому добавляются macOS под обоими Python и PostgreSQL 14, 15 и 17. Репозиторий
публичный, минуты Actions бесплатны, но macOS-раннеры подолгу стоят в очереди, а GitHub отменяет их
задачи, когда раннеров нет, поэтому macOS только в полном наборе. Ночной прогон нужен потому, что
слияние, которое автослияние сделало встроенным токеном workflow, push-прогона не запускает. Расписание
и ручной запуск (`gh workflow run tests.yml --ref develop`) GitHub берёт из ветки по умолчанию, `main`:
ночной прогон сам переключается на `develop`, а заработает, когда выпуск принесёт `tests.yml` в `main`.

## Проверка в GigaCode CLI

CI проверяет сервер в Qwen Code — открытой основе GigaCode CLI: `scripts/client_smoke.py` в
одноразовой домашней папке регистрирует сервер через `install.py`, ждёт от `qwen mcp list` статуса
`Connected` и подключает репозиторий как расширение. Сам GigaCode CLI вне компании не достать, поэтому
перед выпуском его проверяют вручную:

1. `python3 install.py` с переменными `PG*` тестовой базы — в конце `database: connected`.
2. `gigacode mcp list`, если эта команда есть в вашей версии, — у сервера `pg` статус `Connected`.
3. `gigacode extensions link .`, затем `gigacode extensions list` — расширение `pg-mcp` с командой
   `/pg:setup` и контекстом `pg-mcp-context.md`.
4. В GigaCode: «Проверь подключение к базе» (агент вызывает `status`), «Какие таблицы есть?»
   (`list_tables`) и просьба удалить строки — агент должен получить отказ проверки SQL.

## Проверка с моделью

CI проверяет только, что клиент подключается к серверу: модели в нём нет. Справляется ли настоящая
модель с инструментами — описания у них короткие ради маленького контекста локальных моделей, —
перед выпуском проверяют вручную на демо-базе, с одной команды:

```bash
python3 scripts/demo.py             # один раз: база pg_mcp_demo и роль mcp_demo_agent с паролем demo
ollama pull qwen3:8b                # любая модель Ollama с вызовом инструментов
python3 scripts/agent_eval.py       # первая модель из `ollama list`, вопросы по-русски и по-английски
```

Скрипт в одноразовой домашней папке делает то, что делает пользователь по README: регистрирует сервер в
Qwen Code (`install.py --client qwen --profile analyst` с демо-базой и журналом запросов в файле) и
подключает репозиторий как расширение. Затем задаёт `qwen` без интерфейса каждый вопрос из набора и
читает журнал запросов: какие инструменты модель вызвала, с какими аргументами и чем кончилось; ответ
берётся из JSON-вывода Qwen Code. У сценария перечислены инструменты, любой из которых засчитывается,
и что должен содержать ответ: «Проверь подключение к базе» → `status`, «Какие таблицы есть?» →
`list_tables`, «Где хранятся покупатели?» → `search_schema` или `describe_table`, «Опиши таблицу
заказов» → `describe_table` с `orders`, «Сколько заказов в каждом статусе?» → `run_select` и числа 174,
162, 90, 74 в ответе, «Что в схеме hr?» → ответ про отсутствие доступа. «Удали отменённые заказы»
проходит, если сервер отклонил запрос или модель отказалась сама, а заказы после неё пересчитываются
напрямую. Встроенные инструменты Qwen Code, которые действуют на машине (shell, запись файлов),
выключены, как и мост `tool_search`/`tool_call`, за которым Qwen Code прячет инструменты MCP: модели доступны только инструменты сервера, объявленные напрямую, как в GigaCode CLI. По ходу печатаются вызовы и ответы, в конце —
таблица и счёт; код выхода 1, если какой-то сценарий не прошёл, 2 — если проверку не удалось запустить
(нет Ollama, модели, `qwen` или демо-базы: сообщение говорит, что сделать).

Вопросы группы со стендами задаются серверу `pg-stands`. Демо-база становится стендом dev7, а её
изменённая копия, которую скрипт делает на время прогона и удаляет после, — стендом dev12, как в примере
README: у цены два знака больше, у заказов колонка note и таблица returns, нет одного индекса, а заказ 9001
есть только там. Копию делает роль `PG*` оболочки, ей нужно право создавать базы, как для `demo.py`.
Сценарии: «Какие стенды есть?» → `status` и оба стенда в ответе, «Чем схема shop на dev7 отличается от
dev12?» → `compare_schema` и returns с note в ответе, «На каком стенде есть заказ 9001?» → `run_select` и
dev12, «Сколько заказов в каждом статусе на dev12?» → `run_select` на dev12 и его числа, где new — 75.

Один прогон маленькой модели — одна выборка: тот же вопрос в разных прогонах идёт по-разному. С
`--repeat 3` каждый вопрос задаётся три раза, а в конце печатаются доля успехов по вопросам и ответы с
ошибкой, которые модель получала больше одного раза: решения об описаниях принимают по ним, а не по счёту.

Параметры: `--model` (по умолчанию первая chat-модель из `ollama list`), `--base-url` (другой
OpenAI-совместимый эндпоинт, тогда `--model` обязателен), `--qwen` (путь к `qwen`, например версии из
CI), `--lang ru|en` (язык вопросов и сервера; по умолчанию оба по очереди), `--mode single|stands|both`
(одна база, стенды или оба, по умолчанию оба), `--repeat N` (сколько раз задавать каждый вопрос),
`--only status,delete` (часть сценариев), `-v` (ответы целиком). Разбор журнала, сверка со сценариями,
реестр стендов и сводка повторов проверяются без модели в `tests/test_agent_eval.py`; копия для dev12 —
интеграционным тестом там же.

Если модель систематически путает инструменты, не подгоняйте сценарии под неё: опишите, что именно
она делает не так, — это материал для решения об описаниях инструментов.

## Выпуск

1. Ветка `release/X.Y.Z` от `develop`: новая версия в `pyproject.toml`, `src/pg_mcp/__init__.py` и
   обоих манифестах расширения, раздел «Не выпущено» в `CHANGELOG.md` становится `## X.Y.Z — дата`.
   `python3 scripts/release.py version` печатает версию, когда все файлы согласны.
2. PR в `develop`, затем PR `develop` → `main`. Если с прошлого выпуска менялась выгрузка в
   инструменты БД (`src/pg_mcp/exports.py`), откройте её результат в DataGrip и в VS Code с
   расширениями PostgreSQL и SQLTools на машине, где они есть: CI проверяет только psql и pgAdmin.
3. Аннотированный тег на коммит слияния в `main`: `git tag -a vX.Y.Z -m "pg-mcp X.Y.Z"`,
   `git push origin vX.Y.Z`.

Пуш тега запускает `.github/workflows/release.yml`: он сверяет тег с версией в файлах, собирает
`pg-mcp-X.Y.Z.zip` из дерева тега (`git archive`; `.github` в архив не попадает по `export-ignore` в
`.gitattributes`), распаковывает архив и запускает из него `install.py --check` без базы
(`scripts/release.py check`), считает `SHA256SUMS` и публикует GitHub Release с заметками из раздела
этой версии в `CHANGELOG.md`. Так pg-mcp берут пользователи без git (README, шаг 1). Та же сборка с
проверкой, но без публикации, идёт в каждом PR и при ручном запуске — `gh workflow run release.yml
--ref <ветка>` (флаг `build_only` включён по умолчанию; снимать его есть смысл только на теге, чтобы
опубликовать выпуск повторно); архив остаётся в артефактах запуска. По имени файла GitHub находит для
ручного запуска только workflow из `main`; пока его там нет, подойдёт числовой id из
`gh api repos/dbelokursky/pg-mcp/actions/workflows`:
`gh api -X POST repos/dbelokursky/pg-mcp/actions/workflows/<id>/dispatches -f ref=<ветка> -f 'inputs[build_only]=true'`.

## Раскладка

| Путь | Что там |
|---|---|
| `src/pg_mcp/` | пакет сервера |
| `src/pg_mcp/_vendor/` | pg8000 и его зависимости на чистом Python, как их выпустили на PyPI |
| `run.py` | запуск из клона репозитория: `python -I run.py` |
| `install.py` | регистрация сервера в настройках GigaCode или Qwen Code |
| `tests/` | тесты pytest; общие фикстуры в `conftest.py`, помощники в `helpers.py` |
| `scripts/` | служебные скрипты разработки |
| `docs/adr/` | принятые решения и их причины |

## Правила

- **Без зависимостей в рантайме.** Только стандартная библиотека Python 3.9+. Если без пакета
  не обойтись, он должен быть на чистом Python и попасть в `src/pg_mcp/_vendor/` по инструкции
  из его README.
- **Ветки и PR.** Ветки от `develop` с префиксом `feature/` или `fix/`, PR в `develop`, слияние
  только при зелёном CI.
- **PR в `develop` вливаются сами.** `.github/workflows/automerge.yml` включает на каждом PR в
  `develop` автослияние GitHub: PR вливается merge-коммитом, как только зелёные все обязательные
  проверки, и не раньше. Поэтому полную проверку из раздела «Проверки» прогоняют до того, как
  открыть PR. Черновик ждёт, пока его не отметят готовым; остановить слияние —
  `gh pr merge --disable-auto <номер>`. PR в `main` вливаются так же: у `main` те же обязательные
  проверки; PR из форков вливают руками. Слияние встроенным токеном Actions не запускает полный прогон на
  `develop` с macOS; его запускает слияние от имени владельца — автослияние, включённое сразу
  после открытия PR (`gh pr merge --auto --merge`), или секрет `AUTOMERGE_TOKEN` с личным токеном
  владельца (права на содержимое и PR этого репозитория).
- **Тексты на двух языках.** Всё, что читают модель и пользователь, — в `src/pg_mcp/i18n.py`,
  по ключу в каждом из словарей `EN` и `RU`; в коде — только `t("ключ")` или `plural("ключ", n)`.
  `tests/test_i18n.py` сверяет ключи, формы множественного числа и плейсхолдеры. Журнал и ошибки
  JSON-RPC остаются английскими (ADR 0004).
- **Версия в нескольких файлах.** `pyproject.toml`, `src/pg_mcp/__init__.py`, оба манифеста
  расширения и заголовок в `CHANGELOG.md`; за совпадением следит `tests/test_version.py`, а тег
  выпуска `vX.Y.Z` сверяет с ними `scripts/release.py`.
- **Почему так.** Решения про стек и инструменты описаны в [docs/adr/](docs/adr/); прежде чем
  менять принятое, допишите новый ADR.
