# ADR 0006. Много стендов в одной записи

Статус: принято 2026-10-22.

## Контекст

Разработчик работает с десятками стендов: Dev1–Dev50 и ИФТ1–ИФТ3. На каждом стенде несколько баз, в
каждой базе — десятки схем, и у каждой схемы обычно свой пользователь с таким же именем и своим
паролем. Некоторые пользователи читают и соседние схемы, но рассчитывать на это нельзя. Адреса стендов
не подчиняются шаблону. Подключения сейчас хранятся в DBeaver, стенды доступны по VPN.

Запись на каждый стенд (`install.py --name`) не масштабируется: каждая запись приносит модели свой
набор инструментов, около 5 тысяч символов описаний на каждый запрос, а подключений — сотни.

## Решение

| Вопрос | Выбор | Почему |
|---|---|---|
| Сколько записей в агенте | одна запись для всех стендов, обычно `pg-stands` | инструменты описаны один раз, контекст не растёт с числом стендов |
| Как включается | переменная `PG_EXPLORER_MCP_STANDS`: `*` или шаблоны имён стендов через запятую (`dev*,ift2`) | без неё сервер работает как раньше, по переменным `PG*`, что бы ни лежало на диске |
| Где реестр | формат `pg_service.conf` из libpq: секция на подключение с именем `стенд.база.схема` | стандартный формат: те же секции понимает `psql service=dev7.orders.billing` |
| Какие файлы | `PG_EXPLORER_MCP_STANDS_FILE` (по умолчанию `~/.pg-explorer-mcp/stands.conf`, его пишет импорт) и обычный `pg_service.conf` пользователя | сервер только читает; при одинаковых именах побеждает файл импорта |
| Учётные данные | в секции `host`, `port`, `dbname`, `user` (по умолчанию — имя схемы), пароль — в `~/.pgpass` | пароль ищется так же, как раньше; `password=` в секции работает, но не рекомендуется |
| Несколько хостов | `host=h1,h2` с одним `port` или `port=p1,p2`, как в libpq; сервер пробует хосты по порядку и берёт первый, который пустил; пароль ищется на каждый хост отдельно | так DBeaver хранит подключение к стенду с резервным хостом (`h1:6544,h2` и порт 6544), и те же секции понимает psql |
| Что берётся из записи | `PGSSLMODE`, `PGSSLROOTCERT`, таймауты и файл паролей — для всех стендов, если секция не задаёт своё; хост, пользователь и пароль записи — никогда | требование TLS одно на компанию, а чужая учётка на стенде — ошибка |
| Как агент выбирает подключение | аргументы `stand` и `schema`, при повторяющемся имени схемы — `database`; схему, которой нет в реестре, читает учётка базы, читаемой целиком, а если таких баз на стенде несколько, `database` говорит, в какой она | модель не знает о пользователях: сервер сам берёт учётку нужной схемы |
| Структура по всему стенду | системный каталог через любую учётку базы, только по схемам из реестра; для базы с одной учёткой — всё, что она читает | каталог PostgreSQL виден всем; один запрос вместо подключения под каждой схемой |
| Одна учётка на базу | база стенда, у всех секций которой одна учётка (одно подключение из DBeaver — одна секция, названная по учётке: `[ift-caldera.caldera_ift1.cldr_testers_user]`), читается целиком через неё: `schema` принимает любую схему, а список схем и таблиц даёт каталог по правам учётки, как для записи на одну базу; база с несколькими учётками работает только по схемам реестра | на ИФТ одна учётка читает десятки схем, а импорт не знает, какие; реестр, который строже базы, прятал бы их все, тогда как права и так проверяет PostgreSQL |
| Сравнение стендов | `compare_schema` со `stand_a`, `stand_b` и `schema`: структура схемы на обоих стендах из каталога под её учёткой, три запроса на стенд, в ответе только различия — таблицы, колонки, ограничения, индексы; схема, которой нет в базе одного стенда, — ошибка | «чем orders на dev7 отличается от dev12» — один вызов вместо describe_table по каждой таблице на двух стендах; данные не читаются |
| Один эталон против многих | `compare_schema` со `stands` вместо `stand_b`: эталон читается один раз, стенды — по очереди в бюджете 25 секунд, не больше 10; до трёх стендов — полные различия, больше — строка с числами на стенд; недоступный стенд не мешает остальным | «какие стенды отличаются от dev7» — один вызов; подробности на десять стендов не влезут в бюджет ответа |
| Данные | только через учётку нужной схемы, `search_path` — эта схема | права проверяет сама база; без доступа к соседней схеме будет `permission denied` |
| Подключения | открываются по требованию, держится не больше 8, остальные закрываются; подключение ждёт 10 секунд, открытый сокет — не меньше таймаута запроса плюс 5 секунд | сотни соединений не висят; упавший VPN не держит агента по 30 секунд; долгий запрос не обрывается сетью и не запускается повторно |
| Хост не ответил | в пределах одного вызова хост, который не ответил (нет маршрута, таймаут, отказ порта), больше не пробуется ни под одной учёткой; вторая учётка базы пробуется, только когда сервер ответил и отверг первую | клиент ждёт ответа инструмента 30 секунд: стенд из трёх баз за упавшим VPN стоил бы 60 секунд и обрыв вызова вместо подсказки |
| Проверка стенда | `status` со `stand` пробует первую учётку стенда; если сервер её отверг — вторую | сломанная учётка одной схемы не выдаёт весь стенд за недоступный |
| Что видно в ответе | первая строка ответа — `стенд / база / схема`; то же уходит в журнал запросов | всегда понятно, откуда данные |
| Один запрос на нескольких стендах | `stands` в `run_select` и `search_schema`: имена через запятую или шаблон, не больше 10 за вызов; стенды опрашиваются по очереди, в ответе секция на стенд, сбой стенда — строка под его заголовком; строки и совпадения делятся между стендами | «на каком стенде есть заказ» — один вызов, а не десять; клиент ждёт ответа 30 секунд, недоступный стенд стоит таймаут сети, и предел в 10 стендов с 25 секундами на вызов держит ответ в рамках; потоки усложнили бы пул и журнал |

## Ничего не ломать

- Режим стендов включается только переменной `PG_EXPLORER_MCP_STANDS`. Запись без неё работает как раньше.
- Реестр читается снисходительно: нет файла, файл не читается, секция с ошибкой — сервер пропускает
  это, предупреждает в `status` и работает с тем, что удалось прочитать. Если стендов не осталось
  совсем, сервер работает по переменным `PG*`, как раньше.
- Сбой одного стенда — нет сети, неверный пароль — касается только этого стенда.
- Импорт — отдельная команда, сервер его не запускает. Импорт пишет только свой файл реестра и
  дописывает `~/.pgpass`, ничего не удаляя; при любой ошибке не пишет ничего.

## Импорт

`install.py import dbeaver` и `install.py import pg-service <файл>`: по умолчанию предпросмотр — какие
секции `стенд.база.схема` попадут в реестр, сколько паролей в файл паролей, что пропущено и почему, —
запись только с `--write`. Стенд распознаётся по папке DBeaver, имени подключения и хосту регулярным
выражением (по умолчанию `(dev|ift)[-_ ]?\d+`, меняется `--stand-pattern`; разделитель между буквами и
числом отбрасывается, а подключение, где шаблон ничего не нашёл, получает стендом своё имя), база — из
подключения, сначала из его URL, а на месте схемы — его учётка: какие схемы она читает, импорт не знает, и сервер
читает такую базу целиком через неё. Сохранённые пароли DBeaver берутся из `credentials-config.json`: он зашифрован AES-128-CBC
ключом DBeaver по умолчанию, и `src/pg_explorer_mcp/aes.py` реализует этот шифр на чистом Python, без
зависимостей; при защищённом хранилище DBeaver пароли остаются неизвестны и добавляются вручную.
Запись готовит оба файла целиком, потом ставит их на место с датированной копией прежних; файл паролей
только дополняется и обновляется, реестр дополняется или с `--prune` заменяется; при сбое не меняется
ничего. После записи регистрируется запись `pg-stands` с `PG_EXPLORER_MCP_STANDS=*`, запись `pg` не трогается.
При ручном запуске `install.py` в терминале, найдя DBeaver, предлагает показать предпросмотр; агент
делает то же командой `/pg:import` и пишет только после подтверждения пользователя.

Сервер перечитывает реестр, когда его файлы изменились (по времени и размеру, перед каждым вызовом),
поэтому импорт виден без перезапуска агента; если после изменения стендов прочитать не удалось,
остаются прежние, а `status` предупреждает. Файл реестра со строкой `password=`, доступный для чтения
другим пользователям, тоже даёт предупреждение.

## Рассмотренные варианты

- **Запись на стенд** — уже работает через `--name`, но при сотнях подключений съедает контекст модели.
- **Список подключений в описании инструмента** (`enum`) — сотни имён в каждом запросе к модели.
- **Команда «перейти на стенд»** с запоминанием текущего — модель теряет, где она, а параллельные вызовы
  становятся неоднозначными; явный аргумент в каждом вызове надёжнее.
- **Свой формат реестра** (JSON, TOML) — ещё один формат там, где уже есть стандартный.
- **Читать DBeaver при каждом запуске сервера** — сбой разбора чужого формата ломал бы сервер; импорт
  отдельной командой безопаснее.

## Последствия

- Инструменты в режиме стендов принимают `stand`; для данных обязательна и `schema`.
- Запись стендов регистрирует тот же `install.py`: `PG_EXPLORER_MCP_STANDS='*' install.py --name stands`. Проверке
  установки достаточно найденных стендов: дома, без VPN, стенды недоступны, и это не ошибка установки.
- Профиль, язык, бюджет и журнал — общие для всех стендов записи. Если нужны разные профили, можно
  завести несколько записей с разными фильтрами `PG_EXPLORER_MCP_STANDS`.
- Вызов на несколько стендов (`stands`) опрашивает их одновременно, по потоку на стенд, не больше 100 за
  вызов и в пределах 25 секунд: вызов длится столько, сколько самый медленный стенд, а стенд, который за
  это время не ответил, называется в конце ответа. Пул подключений общий для потоков: его учёт идёт под
  замком, а подключение стенда, который ещё отвечает, не закрывается, пока его поток не закончит. Строки
  `run_select` и совпадения `search_schema` делятся между стендами, не меньше 10 на стенд, чтобы ответ
  уложился в бюджет; стенды без строк и без совпадений сворачиваются в одну строку.
- Журнал запросов пишет на такой вызов одну запись, а не по записи на стенд: вызов агента остаётся одной
  строкой с его длительностью, как в ADR 0005. Поле `stands` сопоставляет каждому стенду итог (`ok`,
  `unavailable`, `error`, `skipped`), `rows` — сумма по стендам, `role` и `database` пусты, потому что у
  каждого стенда своя учётка. Запись на стенд размножила бы один вызов на десять строк и потеряла бы
  его длительность; разрез по стендам есть в `stands`.
