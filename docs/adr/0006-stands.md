# ADR 0006. Много стендов в одной записи

Статус: принято 2026-10-22.

## Контекст

Разработчик работает с десятками стендов: Dev1–Dev50 и ИФТ1–ИФТ3. На каждом стенде несколько баз, в
каждой базе — десятки схем, и у каждой схемы обычно свой пользователь с таким же именем и своим
паролем. Некоторые пользователи читают и соседние схемы, но рассчитывать на это нельзя. Адреса стендов
не подчиняются шаблону. Подключения сейчас хранятся в DBeaver, стенды доступны по VPN.

Запись на каждый стенд (`install.py --name`) не масштабируется: каждая запись приносит модели свой
набор инструментов, около 5 тысяч символов описаний на каждый запрос, а подключений — сотни.

## Решение

| Вопрос | Выбор | Почему |
|---|---|---|
| Сколько записей в агенте | одна запись для всех стендов, обычно `pg-stands` | инструменты описаны один раз, контекст не растёт с числом стендов |
| Как включается | переменная `PG_MCP_STANDS`: `*` или шаблоны имён стендов через запятую (`dev*,ift2`) | без неё сервер работает как раньше, по переменным `PG*`, что бы ни лежало на диске |
| Где реестр | формат `pg_service.conf` из libpq: секция на подключение с именем `стенд.база.схема` | стандартный формат: те же секции понимает `psql service=dev7.orders.billing` |
| Какие файлы | `PG_MCP_STANDS_FILE` (по умолчанию `~/.pg-mcp/stands.conf`, его пишет импорт) и обычный `pg_service.conf` пользователя | сервер только читает; при одинаковых именах побеждает файл импорта |
| Учётные данные | в секции `host`, `port`, `dbname`, `user` (по умолчанию — имя схемы), пароль — в `~/.pgpass` | пароль ищется так же, как раньше; `password=` в секции работает, но не рекомендуется |
| Что берётся из записи | `PGSSLMODE`, `PGSSLROOTCERT`, таймауты и файл паролей — для всех стендов, если секция не задаёт своё; хост, пользователь и пароль записи — никогда | требование TLS одно на компанию, а чужая учётка на стенде — ошибка |
| Как агент выбирает подключение | аргументы `stand` и `schema`, при повторяющемся имени схемы — `database` | модель не знает о пользователях: сервер сам берёт учётку нужной схемы |
| Структура по всему стенду | системный каталог через любую учётку базы, только по схемам из реестра | каталог PostgreSQL виден всем; один запрос вместо подключения под каждой схемой |
| Сравнение стендов | `compare_schema` со `stand_a`, `stand_b` и `schema`: структура схемы на обоих стендах из каталога под её учёткой, три запроса на стенд, в ответе только различия — таблицы, колонки, ограничения, индексы; схема, которой нет в базе одного стенда, — ошибка | «чем orders на dev7 отличается от dev12» — один вызов вместо describe_table по каждой таблице на двух стендах; данные не читаются |
| Данные | только через учётку нужной схемы, `search_path` — эта схема | права проверяет сама база; без доступа к соседней схеме будет `permission denied` |
| Подключения | открываются по требованию, держится не больше 8, остальные закрываются; подключение ждёт 10 секунд, открытый сокет — не меньше таймаута запроса плюс 5 секунд | сотни соединений не висят; упавший VPN не держит агента по 30 секунд; долгий запрос не обрывается сетью и не запускается повторно |
| Хост не ответил | в пределах одного вызова хост, который не ответил (нет маршрута, таймаут, отказ порта), больше не пробуется ни под одной учёткой; вторая учётка базы пробуется, только когда сервер ответил и отверг первую | клиент ждёт ответа инструмента 30 секунд: стенд из трёх баз за упавшим VPN стоил бы 60 секунд и обрыв вызова вместо подсказки |
| Проверка стенда | `status` со `stand` пробует первую учётку стенда; если сервер её отверг — вторую | сломанная учётка одной схемы не выдаёт весь стенд за недоступный |
| Что видно в ответе | первая строка ответа — `стенд / база / схема`; то же уходит в журнал запросов | всегда понятно, откуда данные |

## Ничего не ломать

- Режим стендов включается только переменной `PG_MCP_STANDS`. Запись без неё работает как раньше.
- Реестр читается снисходительно: нет файла, файл не читается, секция с ошибкой — сервер пропускает
  это, предупреждает в `status` и работает с тем, что удалось прочитать. Если стендов не осталось
  совсем, сервер работает по переменным `PG*`, как раньше.
- Сбой одного стенда — нет сети, неверный пароль — касается только этого стенда.
- Импорт — отдельная команда, сервер его не запускает. Импорт пишет только свой файл реестра и
  дописывает `~/.pgpass`, ничего не удаляя; при любой ошибке не пишет ничего.

## Импорт

`install.py import dbeaver` и `install.py import pg-service <файл>`: по умолчанию предпросмотр (таблица
«подключение → стенд, база, схема, пользователь», без паролей), запись — с `--write`. При ручном запуске
`install.py`, найдя DBeaver, предлагает показать предпросмотр; агент делает то же командой `/pg:import`
и записывает только после подтверждения пользователя. Подробности — в коде импорта.

## Рассмотренные варианты

- **Запись на стенд** — уже работает через `--name`, но при сотнях подключений съедает контекст модели.
- **Список подключений в описании инструмента** (`enum`) — сотни имён в каждом запросе к модели.
- **Команда «перейти на стенд»** с запоминанием текущего — модель теряет, где она, а параллельные вызовы
  становятся неоднозначными; явный аргумент в каждом вызове надёжнее.
- **Свой формат реестра** (JSON, TOML) — ещё один формат там, где уже есть стандартный.
- **Читать DBeaver при каждом запуске сервера** — сбой разбора чужого формата ломал бы сервер; импорт
  отдельной командой безопаснее.

## Последствия

- Инструменты в режиме стендов принимают `stand`; для данных обязательна и `schema`.
- Запись стендов регистрирует тот же `install.py`: `PG_MCP_STANDS='*' install.py --name stands`. Проверке
  установки достаточно найденных стендов: дома, без VPN, стенды недоступны, и это не ошибка установки.
- Профиль, язык, бюджет и журнал — общие для всех стендов записи. Если нужны разные профили, можно
  завести несколько записей с разными фильтрами `PG_MCP_STANDS`.
