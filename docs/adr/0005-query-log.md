# ADR 0005. Журнал запросов агента

Статус: принято 2026-10-22.

## Контекст

Пользователю и тем, кто отвечает за группу, нужно видеть, что агент делал с базой: какие таблицы
смотрел, какие запросы выполнял и что ему отказали. Сервер работает на машине каждого пользователя,
а не рядом с базой, и пишет только журнал в stderr, который агент обычно никому не показывает.

## Решение

| Вопрос | Выбор | Почему |
|---|---|---|
| Включение | переменная `PG_MCP_QUERY_LOG` с путём к файлу; без неё журнал выключен | по умолчанию на диск ничего не пишется |
| Формат | JSON Lines: одна строка на вызов инструмента | читается `jq`, загружается в любую систему логов |
| Что пишется | время (UTC), пользователь ОС, PID, роль и база, инструмент, аргументы целиком (вместе с текстом SQL), исход (`ok`, `refused`, `error`, `unavailable`, `failed`), текст отказа или ошибки, число строк, которые вернул запрос агента, длительность | этого хватает, чтобы ответить «кто, что, когда и чем кончилось» |
| Что не пишется | сами строки данных и ответы инструментов | журнал не должен становиться копией данных |
| Права на файл | создаётся с правами 600 | литералы в SQL могут содержать персональные данные |
| Запись | файл открывается на каждую строку с `O_APPEND`, строка уходит одной записью | несколько сессий агента пишут в один файл, не перемешивая строки; `logrotate` переносит файл без перезапуска сервера |
| Символические ссылки | ссылка на месте файла отвергается (`O_NOFOLLOW`) | ссылка, подложенная в общую папку, не перенаправит запись в чужой файл |
| Путь | только абсолютный, `~` разрешена | рабочая папка сервера зависит от агента и непредсказуема |
| Сбой записи | вызов инструмента не прерывается; `status` показывает причину, в stderr — предупреждение | журнал вспомогательный, работа агента важнее |
| Ротация | встроенной нет | `logrotate` (с `create`) или перенос файла: сервер создаст новый при следующей записи |

## Чем журнал не является

Файл лежит на машине пользователя, и пользователь может его изменить или удалить. Это журнал
действий агента — для самого пользователя и для разбора случаев, — а не защищённый аудит.
Аудит доступа к данным ведётся на сервере PostgreSQL: `pgaudit` или `log_statement` и
`log_connections`. Соединения сервера помечены `application_name = 'pg-mcp'`, их легко отделить
от остальных.

## Рассмотренные варианты

- **Ротация средствами `logging` (`RotatingFileHandler`)** — неверно работает, когда в один файл
  пишут несколько процессов, а у каждой сессии агента свой процесс сервера.
- **syslog или журнал ОС** — на Linux, macOS и Windows устроены по-разному, пользователям
  сложно настроить и прочитать.
- **Запись в саму базу** — роль агента только читает (ADR 0002), и пусть так и остаётся.
- **Хранить и ответы инструментов** — журнал стал бы копией данных с персональной информацией.

## Последствия

- Журнал включают при установке: `PG_MCP_QUERY_LOG=~/pg-mcp-queries.jsonl python3 install.py`
  переносит переменную в настройки агента.
- В общих сетевых папках (NFS, SMB) дозапись с `O_APPEND` не атомарна: каждому пользователю лучше
  писать в свой файл.
- База ведёт два счётчика — выполненные запросы агента и полученные строки, — чтобы журнал знал,
  сколько строк вернул вызов, не заглядывая в сами данные.
