# ADR 0007. The name pg-explorer-mcp

Status: accepted, 2026-10-26.

## Context

Under the name `pg-mcp` PyPI already has another project with the same purpose: andre-c-andersen/pg-mcp, a fork of
crystaldba/postgres-mcp. It has the same package `pg_mcp` and the same command `pg-mcp`. pip tells projects apart
only by the distribution name. So `pip install -U pg-mcp` would replace a copy installed from git
with someone else's package, and two copies in one environment would overwrite each other's files. A person or an agent who
guesses `uvx pg-mcp` from the name would install a different server. MCP catalogs and raters such as M8ven also mix up
two projects with one name.

The server is already installed for users: clones and unpacked archives, entries in agent settings with
`PG_MCP_*` variables, stand registries in `~/.pg-mcp/`, exports to DBeaver, VS Code and `pg_service.conf`,
a linked Qwen Code extension. The new name must not break any of this.

## Decision

The product is called pg-explorer-mcp. What users have saved is either read under both names or
stays as it was.

| What | Was | Now | Compatibility |
|---|---|---|---|
| Repository | `dbelokursky/pg-mcp` | `dbelokursky/pg-explorer-mcp` | GitHub redirects old links and git URLs |
| Distribution, package, command | `pg-mcp`, `pg_mcp`, `pg-mcp` | `pg-explorer-mcp`, `pg_explorer_mcp`, `pg-explorer-mcp` | clients start `run.py`, which changes together with the package |
| Variables | `PG_MCP_*` | `PG_EXPLORER_MCP_*` | `environment.py`, at the entry point of the server, `install.py` and the scripts, uses the old name if the new one is missing; the new one wins; `install.py` writes only the new ones |
| Answers, log, `application_name` | `pg-mcp` | `pg-explorer-mcp` | — |
| Stands registry folder | `~/.pg-mcp/`, `%APPDATA%\pg-mcp\` | `~/.pg-explorer-mcp/`, `%APPDATA%\pg-explorer-mcp\` | while the new folder has no `stands.conf`, the server, the import and the exports use the old one |
| Export line in `pg_service.conf` | `# pg-mcp export` | `# pg-explorer-mcp export` | the old one is recognised too; an export rewrites such sections under the new one |
| Release archive | `pg-mcp-X.Y.Z.zip`, folder `pg-mcp/` | `pg-explorer-mcp-X.Y.Z.zip`, folder `pg-explorer-mcp/` | when moving to 0.8.0, run `install.py` once from the new folder |
| Extension | `pg-mcp`, `pg-mcp-context.md` | `pg-explorer-mcp`, `pg-explorer-mcp-context.md` | see below |

## What stayed as it was

- **The file `data-sources-pg-mcp.json` and the connection ids** in DBeaver (`postgres-jdbc-pg-mcp-…`) and VS Code
  (`pg-mcp-…`). These tools tie the user's settings to them. With new ids an export would delete the
  old connections and create new ones, and those settings would be lost.
- **The MCP entries** `pg`, `pg-<name>`, `pg-stands` and the `/pg:*` commands. They do not contain the product name, and
  permission rules in the clients refer to them.
- **History**: past CHANGELOG sections and the reasoning of ADR 0001–0006. In the ADRs only references to the
  current setup were corrected: file paths, variable names, `application_name`.

## Extension

When linking (`extensions link`), Qwen Code creates the folder
`~/.qwen/extensions/<name from the manifest>/` holding the path to the extension folder. On every start the client
rereads the manifest at that path and takes the name from the manifest. So after `git pull` the old `pg-mcp/` entry
loads as `pg-explorer-mcp`, without an error and without a duplicate, and the new context file is picked up too.

Removal breaks. `extensions uninstall` looks for the folder by the current name, does not find it and leaves the old
entry. While it is there, `extensions link` answers that the extension is already installed. The only fix is to delete
`~/.qwen/extensions/pg-mcp`. `install.py` names this folder if it
exists but does not touch it itself: it is the client's storage, and its format depends on the client version. The client stores
whether an extension is enabled by name. Anyone who disabled `pg-mcp` will see it enabled again after the move.

## Alternatives considered

- **Rename only the distribution.** Removes the confusion for pip, but the package and the command still
  clash with someone else's, and catalogs and search still show two pg-mcp projects.
- **Ask for the name on PyPI under PEP 541.** Only an abandoned project whose owner cannot be reached
  is handed over this way. That is not the case here.
- **Keep the old names for the variables, the registry folder and the export line.** Nothing would need to be read under two
  names, but the old name would stay in the documentation and settings for good.
- **Keep the extension name `pg-mcp`.** Removal would not break, but the extension would be named differently from the
  product.

## Consequences

- The old variable names, the `~/.pg-mcp/` folder and the `# pg-mcp export` line are read at least until 1.0.
  They can be removed only by a separate decision, with a CHANGELOG note in a release before that.
- `client_smoke.py` and `agent_eval.py` take the extension name and the context file from the manifest. The next
  rename will not require changes to the checks.
- The texts for the model (`i18n.py`, `commands/pg/*.md`, the context file) have changed, so release 0.8.0
  is checked with a run of `scripts/agent_eval.py`.
